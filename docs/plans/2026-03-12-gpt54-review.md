# GPT-5-4 Review: Citations, Clarification & Token Display

Here’s a focused design review on the areas you asked about: **race conditions in clarification, LangGraph compatibility, SSE contract completeness, edge cases, and risk**.

---

# Executive summary

The design is directionally good, but **Feature 2 (interactive clarification)** is the main risk area.

Biggest concerns:

1. **Clarification pause/resume via `asyncio.Event` keyed by `job_id` is fragile**
   - vulnerable to race conditions
   - hard to make correct across reconnects, retries, duplicate submits, multi-worker deployments
   - not a natural fit for LangGraph unless you explicitly model interruption/resumption in graph state/checkpointing

2. **LangGraph compatibility is underspecified**
   - the proposed `_run_graph checks clarifier output and waits` sounds like orchestration outside the graph
   - this can work, but it weakens graph semantics and may break resumability, observability, and future persistence
   - if using LangGraph seriously, clarification should ideally be represented as an interrupt / resumable state transition, not an ad hoc wait in the API layer

3. **SSE contract is incomplete**
   - missing correlation fields, sequencing, terminal-state guarantees, resume/reconnect behavior, and clarification lifecycle events
   - frontend/backend may become inconsistent under reconnect, timeout, duplicate events, or late clarification submissions

4. **Token accounting is likely incomplete/inaccurate**
   - especially for streamed responses and multi-node aggregation
   - “extract after `astream()`” is often not enough unless usage arrives in a final chunk or callback metadata

5. **Citations via regex in markdown are acceptable but brittle**
   - lower risk than clarification, but there are rendering edge cases and prompt-format drift risk

# 1. Clarification race conditions

## Main issue: `asyncio.Event` keyed by `job_id`

This is the highest-risk part of the design.

### Why it’s risky

`asyncio.Event` only signals “something happened”; it does **not** safely carry:
- which clarification request it belongs to
- whether an answer arrived before or after waiting began
- whether the answer is stale
- whether the answer was already consumed
- whether multiple answers were submitted

If you store “answer + event” in a `JobManager`, you can make it work in a single-process happy path, but there are several race windows.

---

## Specific race conditions

### 1) Answer arrives before `_run_graph` starts waiting
Scenario:
- clarifier decides clarification is needed
- SSE event is emitted
- user responds very quickly
- `/clarify` stores answer and sets event
- `_run_graph` only then creates or starts awaiting the event

If the event object is created too late, the signal can be lost unless you also persist the answer separately and check it before waiting.

### Recommendation
Use a **persistent clarification state object** per request, not just an event:
```python
{
  "request_id": "...",
  "status": "pending" | "answered" | "timed_out" | "consumed",
  "question": "...",
  "options": [...],
  "best_guess": "...",
  "answer": "...",
  "created_at": ...,
  "expires_at": ...
}
```
Then:
- create/store this before emitting SSE
- `/clarify` updates this object atomically
- `_run_graph` checks state first, then waits only if still pending

---

### 2) Duplicate clarification submissions
Scenario:
- user double-clicks
- frontend retries due to network issue
- two browser tabs submit different answers

With only `job_id`, backend may accept multiple answers and whichever arrives last wins.

### Recommendation
Introduce a **`clarification_id` / `request_id`** in the SSE event and require it in `/clarify`:
```json
{
  "type": "clarification_needed",
  "job_id": "...",
  "clarification_id": "...",
  "question": "...",
  "options": [...],
  "best_guess": "...",
  "expires_at": "..."
}
```

And:
```json
POST /api/research/{job_id}/clarify
{
  "clarification_id": "...",
  "answer": "..."
}
```

Backend should accept only the first valid answer for that `clarification_id`, or define explicit overwrite semantics. Usually: **first answer wins**.

---

### 3) Late answer after timeout
Scenario:
- backend times out after 30s and proceeds with `best_guess`
- user submits answer at 31s
- `/clarify` succeeds or partially succeeds
- frontend thinks the answer was used, but backend already moved on

### Recommendation
Clarification requests need explicit status transitions:
- `pending`
- `answered`
- `timed_out`
- `resolved_with_best_guess`
- `consumed`

If answer arrives after timeout, return a clear response:
```json
{"status": "expired", "used_answer": false}
```

Also emit an SSE event if useful:
```json
{"type": "clarification_expired", "clarification_id": "..."}
```

---

### 4) Reconnect / page refresh while waiting
Scenario:
- SSE disconnects
- backend is still waiting
- frontend loses the prompt state
- user reconnects and sees no clarification UI

Current design doesn’t specify how the frontend recovers pending clarification state.

### Recommendation
Pending clarification must be part of **job status**, retrievable independently of SSE. Options:
- `GET /api/research/{job_id}` returns current job state including pending clarification
- or SSE replay with event IDs

At minimum, job status should include:
```json
{
  "status": "waiting_for_clarification",
  "pending_clarification": {
    "clarification_id": "...",
    "question": "...",
    "options": [...],
    "best_guess": "...",
    "expires_at": "..."
  }
}
```

---

### 5) Multi-worker / multi-instance deployment
If FastAPI runs with multiple workers or across pods:
- the SSE connection may be handled by one worker
- `/clarify` may hit another worker
- in-memory `asyncio.Event` in `JobManager` will not be shared

This is a major production risk.

### Recommendation
Do **not** rely on in-memory event objects if multi-worker deployment is possible.

Use one of:
- Redis pub/sub + persisted clarification state
- database row + polling/notification
- LangGraph checkpoint + resume invocation
- single-worker guarantee documented as a hard constraint

If you keep in-memory only, call it out explicitly as a limitation:
> Clarification pause/resume only works in a single-process deployment and is not safe across multiple API workers.

---

### 6) Job cancellation while waiting
Scenario:
- user closes session or starts a new job
- old job is cancelled while waiting for clarification
- `/clarify` still arrives later

Need defined behavior.

### Recommendation
Add cancellation-aware state:
- if job is cancelled, clarification requests become invalid
- `/clarify` returns `409` or `410`

---

### 7) Multiple clarification rounds
The design implies one clarification before planning. But what if:
- clarifier asks once
- user answer is still ambiguous
- clarifier wants another round

Current contract doesn’t support this cleanly.

### Recommendation
Either:
- explicitly constrain to **max 1 clarification round**, or
- support repeated rounds with unique `clarification_id`s and sequence numbers

If you want simplicity, I strongly recommend:
> v1 supports at most one clarification round before planning.

---

## Better design pattern for clarification

### Best option: model clarification as graph state + resumable interrupt
If using LangGraph, the cleanest design is:
- clarifier node returns a state indicating `waiting_for_clarification`
- graph execution stops/interupts
- job status persists pending clarification payload
- `/clarify` updates state and triggers a resume from checkpoint

This is much safer than holding an in-process coroutine on `asyncio.Event`.

### If you keep current approach
Minimum fixes:
- add `clarification_id`
- persist clarification state separately from event
- create state before emitting SSE
- make `/clarify` idempotent
- define timeout/late-answer semantics
- define reconnect recovery
- document single-worker limitation or add shared storage

# 2. LangGraph compatibility

## Current concern

The design says:

> `_run_graph` checks clarifier output. If `needs_clarification`, push event to SSE, create an `asyncio.Event`, wait, then continue`

This suggests the pause/resume logic lives in the API runner, not in the graph itself.

That can work, but it has tradeoffs.

---

## Compatibility concerns

### 1) Orchestration outside the graph breaks graph purity
If the graph is supposed to represent the workflow, then “pause for user input” is part of workflow state. Handling it outside the graph means:
- graph state may not fully explain execution state
- tracing/debugging becomes harder
- checkpoint/resume becomes ad hoc
- future migration to durable execution is harder

### 2) Resume semantics are unclear
“Pipeline resumes from planner with the user-provided clarified query” implies:
- the clarifier node has already run
- planner should start next
- state must be mutated outside the graph before resuming

That’s okay if `_run_graph` is manually stepping nodes, but less okay if using compiled LangGraph execution as intended.

### 3) Timeout path may diverge from graph state
If timeout uses `best_guess`, where is that recorded?
- in graph state?
- in job metadata only?
- in emitted messages only?

You want the final state to clearly record whether:
- user answered
- timeout occurred
- best_guess was used

### 4) Streaming + interruption support
If the graph is streamed via LangGraph events, introducing an external wait may complicate event ordering and terminal events.

---

## Recommendation

### Preferred
Represent clarification in `ResearchState`, for example:
```python
class ResearchState(TypedDict):
    query: str
    clarified_query: str | None
    clarification_request: dict | None
    clarification_answer: str | None
    clarification_status: Literal["none", "pending", "answered", "timed_out"]
    token_usage: dict
```

Then:
- clarifier node sets `clarification_request` and `clarification_status="pending"`
- graph interrupts/stops
- API emits `clarification_needed`
- `/clarify` updates persisted state
- graph resumes from checkpoint

### Acceptable fallback
If you don’t want true graph interruption:
- keep clarification as a pre-graph phase
- run clarifier first outside the main graph
- if needed, ask user
- once clarified, start the actual LangGraph pipeline from planner onward

This is often simpler and more honest architecturally than “graph starts, then API pauses it.”

In other words, if clarification is only before planning, consider making it a **preprocessing stage**, not a graph interruption.

That may actually be the best v1.

# 3. SSE contract completeness

Current SSE events listed:
- `node_started`
- `token`
- `table_data`
- `completed`
- `failed`
- proposed `clarification_needed`

This is not yet a complete contract for robust clients.

---

## Missing fields on all events

Every event should likely include at least:
- `type`
- `job_id`
- `timestamp`
- `sequence` or monotonic event number

Strongly recommended:
- `event_id` for dedupe/replay
- `run_id` if jobs can be retried
- `node` where applicable

Without sequencing, reconnect handling and duplicate suppression are hard.

---

## Clarification event contract gaps

Current:
```json
{"type": "clarification_needed", "question": "...", "options": ["A", "B", "C"], "best_guess": "..."}
```

Missing:
- `job_id`
- `clarification_id`
- `expires_at` or timeout_seconds
- whether free text is allowed
- whether options are advisory or exclusive
- max length / validation constraints

Suggested:
```json
{
  "type": "clarification_needed",
  "job_id": "...",
  "clarification_id": "...",
  "question": "...",
  "options": ["A", "B", "C"],
  "best_guess": "...",
  "allow_free_text": true,
  "expires_at": "2026-03-12T12:34:56Z",
  "sequence": 12,
  "timestamp": "..."
}
```

---

## Missing lifecycle events

You likely also need one or more of:

### `clarification_received`
Useful for UI acknowledgement:
```json
{
  "type": "clarification_received",
  "job_id": "...",
  "clarification_id": "...",
  "answer": "...",
  "sequence": 13
}
```

### `clarification_timeout`
If backend proceeds automatically:
```json
{
  "type": "clarification_timeout",
  "job_id": "...",
  "clarification_id": "...",
  "best_guess_used": "...",
  "sequence": 13
}
```

This is better than relying on frontend-local timers or inferred behavior.

### `status`
A generic status event can simplify UI:
```json
{"type": "status", "job_id": "...", "status": "waiting_for_clarification"}
```

---

## Terminal event guarantees

Need to specify:
- exactly one of `completed` or `failed` per job?
- can `completed` happen after `clarification_timeout`? presumably yes
- can `failed` happen while waiting for clarification? yes
- what if SSE disconnects before terminal event?

Document:
- terminal event semantics
- whether events are best-effort or durable
- whether clients should poll final job status if stream ends unexpectedly

---

## Token event / completed event contract

If token usage is only included in `completed`, define shape precisely:
```json
{
  "type": "completed",
  "job_id": "...",
  "message": "...",
  "token_usage": {
    "input": 1234,
    "output": 316,
    "total": 1550
  }
}
```

Include `total` server-side to avoid duplicated frontend logic.

Also define whether token usage is:
- total across all LLM calls in the job
- only final synthesis
- only assistant-visible message

Right now this is ambiguous.

---

## Reconnect semantics

This is a major omission.

Need to define one of:
1. SSE is ephemeral; on reconnect client must fetch job status separately
2. SSE supports replay via `Last-Event-ID`
3. SSE reconnection is unsupported and jobs should be restarted

For a research agent, option 1 is usually enough:
- SSE for live updates
- `GET /job/{id}` for current state snapshot

# 4. Edge cases by feature

## Feature 1: Citations

### Regex-based markdown rendering risks
Using regex to detect `[Source: ...]` inside markdown is okay, but edge cases include:
- citations inside code blocks should not become badges
- partial matches across markdown nodes
- nested punctuation like `([Source: ...])`
- multiple citations adjacent to each other
- malformed output like `[Source: ]`
- title/tool names containing `]` or unusual punctuation

### Recommendation
Prefer parsing only in text nodes, not raw markdown string replacement. If using ReactMarkdown custom renderers, ensure:
- code/pre nodes are excluded
- text-node transformation is localized
- malformed citations fall back to plain text

### Prompt-only citation generation risk
LLM may:
- omit citations
- hallucinate citation labels not present in evidence
- vary formatting

If citations matter, prompt-only is weak enforcement.

### Recommendation
At minimum:
- constrain prompt strongly to exact citation syntax
- consider passing allowed citation labels explicitly
- optionally post-validate generated citations against known evidence labels

Low-to-medium risk overall.

---

## Feature 2: Clarification

### Empty or invalid answer
Need validation:
- blank string
- whitespace only
- answer too long
- answer not matching options when options are intended as fixed choices

If free text is allowed, define max length and sanitization.

### Clarifier returns malformed JSON
The design assumes dual-mode structured output. Need fallback if model returns invalid schema.

Recommendation:
- use structured output parsing with validation
- on parse failure, default to `clarified_query = original query` or `best effort rewrite`
- avoid blocking user due to parser failure

### Clarification prompt shown after job already advanced
Possible under timeout/reconnect races. UI should remove stale prompt if:
- `clarification_timeout`
- `completed`
- `failed`
- `node_started` for planner after clarification phase

### User submits clarification after completed/failed
Must return clear error.

### Security / abuse
Free-text clarification can be prompt injection input. Since it becomes part of the clarified query, that’s expected, but:
- log it carefully
- avoid rendering unsanitized in UI
- avoid treating it as trusted metadata

High risk area overall.

---

## Feature 3: Token display

### Streaming responses may not expose usage the way you expect
Depending on ChatDatabricks/LangChain integration:
- usage may only be available on final response
- `astream()` chunks may not include usage
- some nodes may not expose metadata consistently

### Double counting risk
If a node both streams and later returns a final object with aggregate usage, you may count twice.

### Missing usage in tool calls / retries
If the model retries internally or tool-calling uses extra LLM calls, usage may not be captured unless every invocation path is instrumented.

### Ambiguity of what user sees
Displaying “1,550 tokens” under a message implies that message cost 1,550 tokens. But your design accumulates **job-wide totals** across nodes. That may be misleading.

### Recommendation
Choose one label explicitly:
- “Research run: 1,550 tokens”
- or “Final answer generation: 420 tokens”

Do not attach job-total tokens to a single assistant bubble without clarifying scope.

Medium risk.

# 5. Risk assessment

## High risk
### Interactive clarification implementation
Reasons:
- concurrency/race conditions
- multi-worker incompatibility if in-memory
- unclear LangGraph resume semantics
- reconnect/state recovery gaps

This is the feature most likely to cause production bugs.

---

## Medium risk
### Token usage display
Reasons:
- metadata availability may vary
- aggregation semantics unclear
- easy to mislead users with wrong scope
- possible under/over counting

---

## Low-to-medium risk
### Citation badges
Reasons:
- mostly UI/prompt work
- brittle formatting, but failures are non-fatal
- can degrade gracefully to plain text

# 6. Concrete recommendations

## Recommendation A: simplify clarification architecture for v1
Best practical option:

### Make clarification a pre-graph phase
Flow:
1. receive user query
2. run clarifier outside main LangGraph
3. if no clarification needed, start graph normally
4. if clarification needed:
   - persist pending clarification state
   - emit `clarification_needed`
   - wait for `/clarify` or timeout
5. once clarified, start graph from planner

Why this is better:
- avoids pausing a running graph
- simpler state model
- easier to reason about
- fewer LangGraph compatibility issues

If clarification only happens before planning, this is likely the cleanest design.

---

## Recommendation B: strengthen clarification contract
Add:
- `clarification_id`
- persisted pending state
- explicit statuses
- timeout metadata
- idempotent `/clarify`
- late-answer handling
- reconnect recovery via job status endpoint

---

## Recommendation C: define SSE schema formally
For each event type, specify:
- required fields
- optional fields
- ordering guarantees
- terminal semantics
- reconnect behavior

At minimum, all events should include:
```json
{
  "type": "...",
  "job_id": "...",
  "sequence": 1,
  "timestamp": "..."
}
```

---

## Recommendation D: clarify token semantics
Decide whether token usage means:
1. whole research job
2. final answer generation only
3. visible assistant message only

Then label it accordingly in UI.

Also verify ChatDatabricks usage behavior for:
- `ainvoke`
- `astream`
- structured output calls

---

## Recommendation E: add fallback behavior for malformed clarifier output
If clarifier output fails schema validation:
- do not block the run
- default to original query or best-effort rewrite
- log parse failure

# 8. Final verdict

## Feature 1: Citations
**Approve with minor caution.**
Low risk, but regex rendering should avoid code blocks and malformed matches.

## Feature 2: Clarification
**Do not approve as currently specified without revisions.**
Main blockers:
- race-prone `asyncio.Event` design
- no `clarification_id`
- no reconnect/state recovery story
- unclear multi-worker behavior
- weak LangGraph integration story

## Feature 3: Token display
**Approve with clarification of semantics.**
Need to define scope and verify metadata extraction for streaming paths.

---

# Bottom line

If you want the safest path:

1. **Ship citations first**
2. **Ship token display second**, after defining token scope
3. **Refactor clarification into a pre-graph persisted workflow**, not an in-memory pause inside `_run_graph`
